# ADR-002: Database

Статус: принято.
Дата: 19.08.2026.

## Контекст

Критические переходы откликов, membership, блокировок и удаления требуют ACID, уникальных ограничений и конкурентной сериализации. Целевая нагрузка — 30 RPS, 10 000 аккаунтов. Поиск ограничен ФИО, названием и фиксированными фильтрами.

## Решение

Использовать один managed PostgreSQL-кластер в РФ с writer и standby failover. Каждый backend-модуль владеет отдельной PostgreSQL schema. PostgreSQL также хранит outbox, поисковую read model и инкрементальные 30-дневные агрегаты. Prisma используется как ORM; сложные конкурентные операции могут использовать проверенный parameterized SQL внутри owning module.

Поисковый кластер, шардирование, read replica и partitioning не вводятся до измеряемого триггера. API и worker имеют отдельные pool limits; фоновые операции выполняются bounded batches с timeout.

Минимальные юридические доказательства находятся в отдельной database с отдельными credentials и без внешних FK.

## Альтернативы

- Elasticsearch/OpenSearch: преждевременен для ограниченного поиска и малого объёма.
- Отдельная БД на модуль: усложняет строгие межмодульные инварианты и восстановление.
- Document DB: хуже соответствует реляционным ограничениям и транзакциям продукта.

## Последствия

- PostgreSQL остаётся общей точкой capacity и требует метрик wait events, locks и pool saturation.
- Полный rebuild агрегатов запрещён в пике; mixed load/soak test обязателен.
- Read replica рассматривается после query/index tuning при устойчивом нарушении capacity budget или p95.

## Триггер пересмотра

Два последовательных нагрузочных теста нарушают p95 после оптимизации либо DB CPU/read latency превышают 70% capacity budget не менее 15 минут.
