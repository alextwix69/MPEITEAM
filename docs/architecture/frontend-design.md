# Frontend Application Design — «Команда.МЭИ»

Статус: проектный документ. Описывает дизайн фронтенд-приложения MVP без реализации кода.

Уточнение реализованного auth slice (TASK-005): регистрация находится на `/registration`, ожидание/повтор письма — `/registration/check-email`, подтверждение — `/verify-email`. Упоминания `/register` и `/confirm-email` ниже обозначают соответствующие проектные экраны, а не дополнительные runtime routes. Добавлены `/login`, `/forgot-password`, `/reset-password` и минимальный `/account` с server-side session check через API. После подтверждения доступна главная; editor профиля остаётся следующему slice. Login не требует предварительной session/CSRF; после успеха выполняются `/me` и `/auth/csrf`. Account screen показывает только разрешённое текущее состояние, включая ограниченные `unverified/deleting`, и выход. API остаётся источником authorization; Next.js не читает БД. BroadcastChannel передаёт между вкладками только сигнал обновления auth state, без секретов.

Источники:

- `docs/product/product-spec.md`, `docs/product/idea.md`, `docs/product/requirements.md`;
- `docs/architecture/api-contracts.md`, `docs/architecture/data-model.md`, `docs/architecture/system-design.md` (§3 Frontend architecture);
- `docs/adr/ADR-001-frontend-framework.md`, `ADR-003-authentication.md`, `ADR-007-media-and-report-evidence.md`, `ADR-008-api-compatibility.md`.

Документ проектирует UI и клиентское поведение, не переносит бизнес-правила и авторизацию в клиент: они повторно проверяются backend (см. `system-design.md` §3).

## 1. Обзор и принципы

### 1.1 Стек (зафиксирован ADR-001)

- Next.js App Router, React, TypeScript strict.
- TanStack Query — server state (fetch, кэш, инвалидация, refetch, optimistic-обновления).
- React Hook Form + Zod — формы и клиентская валидация.
- Tailwind CSS + shadcn/ui — presentation layer.
- REST `/api/v1` — источник истины. Socket.IO — только hint-события (инвалидация query cache); после reconnect синхронизация через REST.
- Redux и отдельный BFF не вводятся.

### 1.2 Принципы проектирования

1. **REST — источник истины.** Изменение фиксируется только после успешного ответа REST; optimistic-обновления обязаны откатываться при ошибке.
2. **Авторизация только на сервере.** Клиент использует флаги прав только для отображения UI, но не как защиту.
3. **Один responsive web client.** Desktop и mobile — одни маршруты и компоненты.
4. **UI на русском** (NFR-023), идентификаторы и имена типов — на английском.
5. **Доступность и клавиатура** — сквозное требование (NFR-014).
6. **Состояния — явные.** Loading / Empty / Error / Partial (модерация, «Удаляется», блокировка) проектируются для каждого экрана.
7. **Идемпотентность.** Повторяемые команды используют `Idempotency-Key`; клиент переживает повторы и retry без дублей.

### 1.3 Сквозные механики клиента

- **HTTP-обёртка**: base path `/api/v1`, cookies `SameSite=Lax`; для unsafe-методов — CSRF-токен (заголовок `X-CSRF-Token`) и проверка allowlisted `Origin`.
- **Обработка ошибок**: единый маппер `{ error: { code, message, requestId, details } }` → русское сообщение + следующее действие (NFR-012). Стабильные коды используются для точечной логики (например `EVIDENCE_UNAVAILABLE`).
- **Идемпотентность**: генерация `Idempotency-Key` (UUID) на клиенте на одну логическую операцию и переиспользование при retry.
- **Realtime**: Socket.IO-события (`notification.created`, `message.created` и т.п.) только инвалидируют/обновляют TanStack Query; после reconnect — полная синхронизация через REST.

## 3. Пользовательские потоки (user flows)

Потоки соответствуют journeys J-01…J-06 спецификации; каждый раскладывается на экраны и переходы.

### 3.1 J-01 Регистрация и резюме

`/register` (wizard: роль → почта → пароль → отдельные согласия) → письмо подтверждения → `/confirm-email` → `/profile/edit` (обязательные поля профиля) → `/profile/resumes` (основное резюме, автозаполнение «Обо мне»/проекты/теги) → при необходимости `/profile/resumes/new` (до 5 дополнительных).

Ограничения: студент/преподаватель — только `@mpei.ru` (FR-002); работодатель — любой корректный адрес (FR-003); возраст 18+ и согласия — отдельные непредустановленные отметки (FR-001, FR-153); до подтверждения почты доступ ограничен (FR-152).

### 3.2 J-02 Отклик и решение

`/opportunities` → `/opportunities/[id]` → кнопка «Откликнуться» → `ResumeSelectDialog` (выбор основного/доп. резюме) → отправка отклика (статус «На рассмотрении»). Получатель: `/notifications` (вкладка «Отклики») → `/applications/[id]` → «Принять»/«Отклонить». Принятие → автоматический переход в контекстный чат `/messages/[id]`.

Ограничения: на своё объявление откликаться нельзя (FR-061); повторный отклик — через 3 суток при рассмотрении/отклонении, запрещён после принятия (FR-081…FR-083); решение необратимо (FR-078).

### 3.3 J-03 Команда и её отклик

`/teams/new` → `/teams/[id]` (оформление) → приглашения `/teams/[id]/members` или приём заявок `/teams/[id]/applications` → объявление от имени команды `/opportunities/new` → отклики во вкладке уведомлений команды → принятие → командный чат (доступен лидеру).

### 3.4 J-04 Личный мессенджер

`/messages` → `/messages/[id]` → текст/фото → статус прочтения → редактирование (метка «Изменено») → удаление сообщения → удаление чата (у себя / у обоих) → при нежелательном контакте «Заблокировать» (`ReportDialog`/`ConfirmDialog`, личный чёрный список).

### 3.5 J-05 Событие команды

`/teams/[id]/events/new` (дата, время, часовой пояс) → публикация → подписчики видят в `/calendar`; изменение/отмена → уведомления подписчикам.

### 3.6 J-06 Модерация

Создание/редактирование публичного контента → автомодерация → при возврате: `ContentStatusBanner` с причиной → исправление → повторная проверка. Автор может обжаловать (`AppealDialog`). Модератор работает в `/moderation`, `/moderation/reports`, `/moderation/appeals`.

### 3.7 Сквозные навигационные правила

- Неавторизованный → `/login`; после входа — redirect на исходный маршрут (deep-link).
- Неподтверждённый аккаунт → только `/confirm-email`, `/login`, `/forgot-password`, `/reset-password`.
- Состояние «Удаляется» → только `/settings/data` (восстановление) и выход (FR-160).
- Отсутствие прав на маршрут → экран «Нет доступа» (403) с пояснением и действием.

## 4. Layouts

### 4.1 `AuthLayout` (public)

- Центрированная колонка (карточка формы), логотип, ссылки «Вход»/«Регистрация»/«Восстановление».
- Нет навигации приложения; фокус на одной задаче.
- Используется: `/login`, `/register`, `/confirm-email`, `/forgot-password`, `/reset-password`.

### 4.2 `AppShell` (авторизован)

- Обёртка всех закрытых маршрутов. Содержит: `Header`, `SideNav` (desktop) / `BottomNav` (mobile), слот контента.
- Содержит глобальные `Toaster` (уведомления) и `StatusBanner` (состояние аккаунта/контента).
- Middleware/guard на layout-уровне проверяет сессию и состояние аккаунта (не бизнес-логика — только маршрутизация).

Структура `Header`: логотип, глобальный поиск (люди/объявления), `NotificationsBell` (счётчик непрочитанного), `UserMenu` (профиль, команды, настройки, выход).

### 4.3 Detail layouts

- `EntityLayout` (общий каркас детальной страницы): заголовок, метаданные автора/команды, основная колонка, боковая панель действий.
- Применяется к `/opportunities/[id]`, `/people/[id]`, `/teams/[id]`, `/teams/[id]/events/[eventId]`.

### 4.4 `ModerationLayout`

- Для модераторов: под-навигация «Очередь | Жалобы | Обжалования», `ModerationStatusFilter`.
- Контент с `Cache-Control: no-store` для evidence; одноразовые короткоживущие ссылки на вложения.

### 4.5 Chat layout

- Двухпанельный на desktop (список чатов + активный чат), одна панель на mobile (список → чат с возвратом).

## 6. Управление состоянием

### 6.1 Server state (TanStack Query)

Владеет всеми данными, полученными по REST. Ключи строятся по схеме `[domain, entity, params]`. Соглашения:

- Списки с cursor pagination хранятся как инкрементальные страницы (`useInfiniteQuery`).
- Инвалидация по префиксу домена (например `['opportunities']`) после мутаций.
- `staleTime`/`gcTime` умеренные; при возврате на вкладку — мягкий refetch.
- Realtime-событие инвалидирует конкретный ключ; полный refetch только после reconnect.

Основные домены кэша: `session` (текущий пользователь), `profile`, `resumes`, `catalog` (теги), `searchPeople`, `searchOpportunities`, `opportunity`, `teams`, `team`, `members`, `applications` (входящие), `teamApplications`, `subscribers`, `events`, `calendar`, `conversations`, `conversation` (сообщения), `notifications`, `reports`, `moderationQueue`, `appeals`, `blacklist`, `uploads`.

### 6.2 Local state (React state / React Hook Form)

Только UI-состояние, не источник истины:

- состояние диалогов и шторок (открыто/закрыто, выбранная сущность);
- текущая вкладка, выбранные фильтры до применения (или синхронизированные с URL query);
- черновики форм (при необходимости — в `sessionStorage` для восстановления после потери страницы);
- optimistic-список сообщений и статусы отправки (pending/sent/failed);
- прогресс загрузки изображений;
- выбор резюме в диалоге отклика/заявки;
- активный `Idempotency-Key` текущей операции.

### 6.3 Realtime (Socket.IO)

- Handshake: только WSS, same-origin; сервер проверяет сессию и состояние аккаунта до `connection`.
- Клиент не доверяет содержимому broadcast-события: использует только `type` + `resourceId` как hint, затем invalidate/refetch соответствующего query.
- Подписка на user/conversation rooms; после `logout`/revoke — разрыв сокета.
- События интереса: `notification.created`, `message.created`, `application.decided`, `conversation.created`, `moderation.decided` и т.п.

## 7. Формы и валидация

React Hook Form + Zod. Клиентская валидация улучшает UX, но не заменяет серверную (все инварианты проверяются backend). Каждая форма имеет Zod-схему, маппинг ошибок и состояния.

| Обжалование | `AppealDialog` | причина (FR-140) |
| Удаление аккаунта | `/settings/data` | подтверждение, следствия (FR-143…FR-147) |
| Настройки данных | `/settings/data` | исправление/выгрузка/прекращение обработки/удаление (FR-143) |

### 7.2 Общие правила валидации

- Подсчёт и лимиты символов/элементов показываются live (счётчики «N из M»).
- Ошибки связываются с полем (`aria-describedby`, фокус на первом невалидном поле).
- Клиент валидирует формат и лимиты; сервер — права, инварианты, конфликты.
- Идемпотентные команды: один `Idempotency-Key` на операцию, повтор при retry с тем же ключом.
- Загрузка изображений валидируется до отправки (MIME, размер, формат) и обрабатывается по flow `POST /uploads` → PUT → `POST /uploads/{id}/complete` → polling `GET /uploads/{id}`.

## 8. Состояния интерфейса

### 8.1 Loading states

- **Начальная загрузка экрана**: skeleton-карточки, повторяющие итоговую раскладку (не пустой белый экран).
- **Кнопки-действия**: spinner + disabled во время выполнения; подпись действия меняется («Отправка…», «Сохранение…»).
- **Пагинация/бесконечный скролл**: индикатор внизу списка, кнопка «Показать ещё».
- **Загрузка изображения**: прогресс-бар и preview; после загрузки — polling статуса `GET /uploads/{id}` (processing → ready/approved/moderation_pending).
- **Отправка сообщения**: optimistic-сообщение со статусом отправки (часики/галочка/ошибка) без блокировки ввода.
- **Модерация публикации**: `ModerationStatusBadge` = `pending` («На проверке») сразу после создания/правки (FR-050, FR-055, ERR-006).

### 8.2 Empty states

Отличаются от ошибок (FR-043, ERR-005). Содержат пояснение + CTA-действие:

- пустая выдача поиска (люди/объявления) — «Ничего не найдено. Измените фильтры» + сброс фильтров;
- нет откликов / заявок / приглашений — «Пока пусто» + ссылка на действие;
- нет чатов — CTA «Найти людей или объявления»;
- нет команд — CTA «Создать команду»;
- календарь пуст — «Подпишитесь на команды, чтобы видеть события»;
- чёрный список пуст;
- очередь модерации пуста.

### 8.3 Error states

Единый маппер кода ошибки → русский текст + следующее действие (NFR-012). Обязательные случаи:

- `401` — сессия истекла → предложение войти заново.
- `403` / нет прав (ERR-011) — «Недостаточно прав» без раскрытия чужого объекта.
- `404` — объект не найден или недоступен.
- Ошибка сети/`5xx` — `ErrorState` с кнопкой «Повторить» (retry query).
- Ошибка поиска vs пустая выдача (ERR-005).
- `EVIDENCE_UNAVAILABLE` (жалоба на удалённый контент) — специфичное сообщение модератору.
- Ошибка отклика (ERR-007) — не создаёт статус, кнопка активна для повтора.
- Недоступное решение (ERR-008) — показать актуальный статус.
- Ошибка создания чата после принятия (ERR-009) — статус сохранён, показать повтор создания.
- Превышение лимита (ERR-004) — конкретное ограничение.
- Ошибка загрузки фото (ERR-013/013a) — файл не доставлен, сообщение не считается отправленным.
- Заблокированный отправитель (ERR-014) — взаимодействие не доставляется, понятное сообщение.
- Конфликт действий (ERR-018, EC-012/015b) — показать актуальное согласованное состояние.
- Невалидная дата события (ERR-012).
- Ошибка фиксации согласия (ERR-003a) — регистрация не завершается.

Глобально: `ErrorBoundary` на уровне route для непредвиденных ошибок + запись `requestId` в сообщение.

### 8.4 Optimistic updates

Применяются только там, где откат безопасен и не нарушает инварианты:

- **Отправка сообщения**: optimistic-append с `pending` → `sent` при успехе, `failed` + «Повторить» при ошибке; дедупликация по `Idempotency-Key`.
- **Пометить уведомления прочитанными**: оптимистичное скрытие бейджа с откатом при ошибке.
- **Подписка/отписка на команду**: оптимистичное переключение с откатом.
- **Добавление/удаление в чёрный список**: оптимистично с откатом.
- **Удаление чата у себя**: оптимистичное скрытие из списка (EC-018).
- **Редактирование сообщения**: оптимистично с меткой «Изменено», откат при ошибке.

Намеренно **не** оптимистичны (необратимы/требуют серверного подтверждения): принять/отклонить отклик (FR-078), решение по заявке, удаление аккаунта/команды, публикация контента (зависит от модерации). Для них — pending-состояние кнопки и явный результат.

## 9. Аутентификация и разрешения

### 9.1 Authentication states

| Состояние | Доступ | Интерфейс |
|---|---|---|
| `unauthenticated` | только public routes | redirect на `/login` |
| `unverified` (email не подтверждён) | `/confirm-email`, `/login`, `/forgot-password`, `/reset-password` (FR-152) | `StatusBanner` «Подтвердите почту», кнопка «Отправить повторно» |
| `active` | полный доступ по роли/правам | обычный `AppShell` |
| `deleting` (запрос удаления) | только `/settings/data` (восстановление) и выход (FR-144, FR-160) | `StatusBanner` с датой окончательного удаления, CTA «Восстановить аккаунт» |
| `deleted` | нет | экран «Аккаунт удалён» |

Определение состояния: `GET` текущей сессии (server state `session`); guard на layout-уровне маршрутизирует по состоянию, не выполняя бизнес-логику.

### 9.2 Permission states

Флаги получаются из session/entity DTO и используются **только для отображения**; авторизация повторяется сервером.

- **Роль пользователя** (студент/преподаватель/работодатель) — влияет на поля профиля, но не на базовые действия (BR-002, P-01…P-03).
- **Автор объявления** — `edit`, «снять», «удалить», «решать по отклику» (FR-053…FR-057).
- **Лидер команды** — управление профилем, участниками, заявками, приглашениями, подписчиками, чёрным списком, объявлениями, событиями, командным чатом (FR-088…FR-100, permissions matrix).
- **Участник команды** — без управленческих прав (FR-092); отображается в составе.
- **Модератор** — `/moderation`, `/moderation/reports`, `/moderation/appeals`; узкие permissions: `reports.review`, `appeals.review`, `evidence.view`, `moderation.escalated_review` (ADR-003, data-model).
- **Блокировка (blacklist)** — скрытие кнопок отклика/заявки/нового чата; существующая история сохраняется (FR-127, FR-100).
- **Неподтверждённый/удаляемый аккаунт** — скрытие всех форм создания/изменения/отправки.

UI-правила: отсутствие права → скрытие действия либо disabled с пояснением; прямой переход на запрещённый маршрут → экран «Нет доступа».

## 10. Responsive behavior

- Базовые breakpoints: mobile `<640px`, tablet `640–1024px`, desktop `≥1024px`; основные journeys корректны от 360px (TNFR-014, NFR-013).
- **Навигация**: `SideNav` на desktop → `BottomNav` (5–6 ключевых пунктов) на mobile; `Header` упрощается.
- **Списки/карточки**: многоколоночная сетка на desktop → одна колонка на mobile.
- **Detail-страницы**: двухколоночная (контент + боковая панель действий) → одна колонка, действия в sticky-панели снизу.
- **Диалоги**: modal на desktop → полноэкранная шторка (bottom sheet) на mobile.
- **Чат**: двухпанельный → одна панель с возвратом.
- **Таблицы/очереди модерации**: строки → карточки.
- **Изображения** адаптируются (`srcset`/размеры), не превышают Full HD (FR-049, FR-118).
- Touch-friendly размеры элементов (≥44px), без hover-only действий.

## 11. Accessibility requirements (NFR-014)

- **Клавиатура**: все journeys выполнимы с клавиатуры; видимый focus; корректный порядок табов; «Skip to content».
- **Семантика**: `header/nav/main/footer`, заголовки по уровням, списки, `button` vs `link`, `aria-current` для активной навигации.
- **Формы**: `label`/`aria-label` для каждого поля, ошибки через `aria-describedby`/`aria-invalid`, фокус на первом невалидном поле.
- **Диалоги**: фокус-ловушка, `role="dialog"`/`aria-modal`, возврат фокуса, закрытие по Esc.
- **Live-регионы**: `aria-live="polite"` для новых сообщений, статусов отправки, уведомлений (не спамить).
- **Читаемость**: контраст текста, альтернативный текст изображений, подписи к иконкам.
- **Уведомления**: не полагаться только на цвет; текстовые подписи статусов.
- **Движение**: уважать `prefers-reduced-motion` (спиннеры/анимации).
- **Целевые размеры** и фокус соответствуют мобильным и клавиатурным сценариям.
- Проверка основными journeys через Playwright: desktop/mobile, клавиатура, поддерживаемые браузеры (ADR-001, TNFR-014).

## 12. Постраничное описание

Для каждой страницы указаны: Purpose, Data requirements, User actions, States, Components, Errors.

### 12.1 Аутентификация

#### /login — Вход

- **Purpose**: вход по почте и паролю (FR-006).
- **Data requirements**: форма входа; CSRF-токен; сессия (после успеха).
- **User actions**: ввести email/пароль, отправить; ссылки «Регистрация», «Восстановить доступ».
- **States**: idle; submitting; error (неверные данные — общее сообщение без раскрытия); redirect после успеха на исходный маршрут.
- **Components**: `AuthLayout`, `FormField`, `Toast`, ссылки.
- **Errors**: некорректные данные (ERR-003), заблокированный/неподтверждённый аккаунт (перенаправление на `/confirm-email`), сеть.

#### /register — Регистрация

- **Purpose**: создание аккаунта (FR-001…FR-004, FR-152, FR-153).
- **Data requirements**: справочник ролей; правила домена почты; тексты согласий (пользовательское соглашение, обработка ПДн, распространение).
- **User actions**: wizard — выбор роли → email → пароль → отдельные чекбоксы возраста и согласий (без предустановки) → отправка.
- **States**: шаги (`Stepper`); submitting; ошибка фиксации согласия (ERR-003a); успех → «Проверьте почту».
- **Components**: `AuthLayout`, `Stepper`, `ConsentCheckbox`, `FormField`, `RoleBadge`.
- **Errors**: неверный домен (EC-002), некорректный email, слабый пароль, неснятые согласия/возраст (EC-003a/003b), уже занятый email.

#### /confirm-email — Подтверждение почты

- **Purpose**: активация по ссылке из письма, повторная отправка (FR-004, FR-005, FR-152).
- **Data requirements**: состояние подтверждения (token/состояние аккаунта).
- **User actions**: переход по ссылке (активация), «Отправить письмо повторно».
- **States**: подтверждается; успех (→ `/profile/edit`); истёкшая/невалидная ссылка (ERR-002) → запросить новую; уже подтверждено.
- **Components**: `AuthLayout`, `StatusBanner`, `Toast`.
- **Errors**: истёкшая ссылка (ERR-002), невалидный токен, сеть.

#### /forgot-password — Восстановление доступа

- **Purpose**: запрос письма восстановления (FR-007).
- **Data requirements**: форма email.
- **User actions**: ввести email → отправить.
- **States**: idle; submitting; успех («Проверьте почту») — нейтральное сообщение без раскрытия существования аккаунта.
- **Components**: `AuthLayout`, `FormField`.
- **Errors**: некорректный email; сеть.

#### /reset-password — Новый пароль

- **Purpose**: установка нового пароля по ссылке (FR-007, NFR-002).
- **Data requirements**: валидная ссылка; форма нового пароля.
- **User actions**: ввести новый пароль → сохранить.
- **States**: idle; submitting; успех → `/login`; истёкшая ссылка.
- **Components**: `AuthLayout`, `FormField`.
- **Errors**: истёкшая/невалидная ссылка, слабый пароль.

### 12.2 Главная

#### / — Главная (обзор)

- **Purpose**: точка входа после логина: сводка и быстрые действия.
- **Data requirements**: `session`, сводка непрочитанного, мои команды, ближайшие события календаря, последние чаты, полнота профиля/основного резюме.
- **User actions**: переходы к поиску людей/объявлений, чатам, календарю, командам; CTA «Заполнить резюме» при неполноте.
- **States**: loading; empty (новый пользователь) — onboarding-подсказки; error.
- **Components**: `AppShell`, карточки-сводки, `StatusBanner`, `EmptyState`.
- **Errors**: ошибка загрузки сводки → retry (частичный отказ не блокирует остальные блоки).

### 12.3 Объявления

#### /opportunities — Каталог и поиск объявлений

- **Purpose**: поиск/просмотр объявлений по названию, тегам, данным автора; сортировка (FR-036…FR-042).
- **Data requirements**: список объявлений (cursor pagination), справочник тегов (`catalog`), фильтры роли/института/кафедры, сортировка по популярности/новизне; состояние фильтров — в URL query.
- **User actions**: ввод поиска, выбор тегов/фильтров, сортировка, сброс фильтров (FR-042), переход к `/opportunities/[id]`, «Создать объявление».
- **States**: loading; empty (пустая выдача ≠ ошибка, FR-043); error; подгрузка следующих страниц; у командных объявлений фильтры роли/института/кафедры не применяются (EC-009, FR-039).
- **Components**: `AppShell`, `SearchBar`, `FilterPanel`/`FilterChip`, `SortSelect`, `OpportunityCard`, `CursorPagination`/`InfiniteScroll`, `EmptyState`, `ErrorState`, `LoadingSkeleton`.
- **Errors**: ошибка поиска (ERR-005) → retry; превышение лимита; сеть.

#### /opportunities/new — Создание объявления

- **Purpose**: создание личного или (для лидера) командного объявления (FR-044, FR-059).
- **Data requirements**: справочник из 22 типов + «Другая активность»; справочник тегов; upload session для картинки; команды пользователя (для выбора авторства).
- **User actions**: заполнить название/описание/картинку/контакт/теги/тип; выбрать авторство (личное/команда); отправить (публикация только после модерации).
- **States**: заполнение; загрузка изображения (прогресс); submitting; после успеха — статус `moderation_pending` (ERR-006 — не показывать как опубликованное).
- **Components**: `EntityLayout`/форма, `FormField`, `ImageUpload`, `TagSelect`, `TypeSelect` (с полем для «Другая активность»), `ConfirmDialog`.
- **Errors**: валидация (ERR-004 — лимиты), ошибка загрузки фото (ERR-013), сбой публикации.

#### /opportunities/[id] — Объявление (деталь)

- **Purpose**: просмотр объявления, авторство, профиль автора/команды, отклик (FR-052…FR-054, FR-060).
- **Data requirements**: объявление (текущая одобренная версия), авторство (личное/командное), мини-профиль автора/команды, состояние отклика текущего пользователя (можно ли откликнуться, срок повторного отклика).
- **User actions**: «Откликнуться» (`ResumeSelectDialog`); открыть профиль автора `/people/[id]` или команды `/teams/[id]`; автор — «Редактировать»/«Снять»/«Удалить».
- **States**: loading; empty/404; moderation (для автора — статус версии); «отклик отправлен»; «повторный отклик недоступен до …» (EC-010/011); блокировка (ERR-014).
- **Components**: `EntityLayout`, `OpportunityCard` (деталь), `ModerationStatusBadge`, `ContentStatusBanner`, `ResumeSelectDialog`, `ConfirmDialog`.
- **Errors**: 404; нет прав на редактирование (ERR-011); ошибка отклика (ERR-007); заблокированный отправитель (ERR-014); снято/удалено.

#### /opportunities/[id]/edit — Редактирование объявления

- **Purpose**: правка объявления; каждая новая версия повторно проходит модерацию (FR-055).
- **Data requirements**: текущая версия объявления; справочники; upload.
- **User actions**: изменить поля → сохранить; «Снять с публикации», «Удалить».
- **States**: заполнение; submitting; после сохранения — `moderation_pending`; до решения видна последняя одобренная версия (FR-055).
- **Components**: как у `/new` + `ContentStatusBanner`, `ConfirmDialog`.
- **Errors**: лимиты (ERR-004), модерация отклонила (ERR-016 — причина + повторная отправка), нет прав.

### 12.4 Поиск людей

#### /people — Поиск людей

- **Purpose**: поиск по ФИО и фильтрам (теги, роль, институт, кафедра), сортировка по активности (FR-033…FR-035).
- **Data requirements**: список пользователей (cursor), справочник тегов, справочники институтов/кафедр; фильтры в URL.
- **User actions**: ввод ФИО, фильтры, сортировка по активности (возр/убыв), переход к `/people/[id]`.

#### /people/[id] — Публичный профиль пользователя

- **Purpose**: просмотр профиля и видимых резюме другого пользователя (FR-028).

- **User actions**: переход к резюме; «Написать сообщение» (создание чата, если не заблокирован); «Заблокировать»/«Пожаловаться» (`ReportDialog`); «Пригласить в команду» (лидер).

#### /profile/resumes — Мои резюме (список)

## 13. Сквозные механики (сводка)

- **CSRF/origin**: unsafe-запросы несут `X-CSRF-Token` (полученный от сервера) и проходят проверку allowlisted `Origin`; cookie-сессия `HttpOnly`/`Secure`/`SameSite=Lax` не читается JS.
- **Idempotency**: повторяемые команды (создание отклика/сообщения/команды/жалобы, решения, membership, завершение upload, запрос удаления) отправляются с одним `Idempotency-Key` на операцию.
- **Upload media**: `POST /uploads` → пресигнед PUT → `POST /uploads/{id}/complete` → polling `GET /uploads/{id}` до `ready`/`approved`/`moderation_pending`/`failed`; для `public_content` публикация только после `approved`.
- **Отображение статуса модерации**: автор видит `ModerationStatusBadge`/`ContentStatusBanner` на своих объектах (pending/approved/rejected, причина, «Исправить»/«Обжаловать»); последняя одобренная версия остаётся видимой до решения (BR-021).
- **Realtime-гинт**: `Socket.IO` событие → invalidation query → REST refetch; клиент не применяет payload события как источник истины.
- **Pagination**: большие списки — cursor pagination (`CursorPagination`/`InfiniteScroll`), стабильный порядок сортировки (FR-035, FR-040, FR-041).

## 14. Допущения и открытые вопросы

Допущения (не противоречат спецификации, требуют подтверждения на этапе реализации):

1. Точный состав сводки на `/` (главная) — агрегация «подсказок», а не самостоятельная бизнес-сущность.
2. Деление фильтров/сортировки между `/opportunities` и `/people` в отдельные маршруты (`search` feature); каталог объявлений совмещён с поиском.
3. Объединение «приглашений» в `/teams/[id]/members`, а «заявок» — в `/teams/[id]/applications`.
4. Глобальный поиск в `Header` отправляет на `/people` или `/opportunities` с предзаполненным запросом.
5. Набор Socket.IO-событий (`notification.created`, `message.created`, `application.decided`, `conversation.created`, `moderation.decided`) подлежит уточнению в backend-контракте.
6. Конкретные поля DTO и endpoint-инвентарь (`/api/v1/*`) доопределяются по мере feature implementation; frontend зависит от стабильности DTO (ADR-008).

Открытых продуктовых вопросов по спецификации нет (`product-spec.md`, «Open questions»). Новые вопросы фиксируются как изменения спецификации до реализации.
